Standards as Tooling

Turning engineering standards from unread documents into things engineers actually run — specs, scaffolds, and agent plugins that audit and generate against the rules.

TypeScriptAWS CDKCLIClaude CodeTemplatesPre-commit
S
Situation

In a fast-moving startup, engineering standards live in wikis nobody reads, and each engineer is heavily leveraged across multiple services — so there's no structural moment for knowledge to disperse. The result is drift: every service solves the same problems differently, and quality depends on who wrote it.

T
Task

Make standards executable — encode them where engineers already work (the toolchain and the agent layer) so compliance is the path of least resistance rather than an act of discipline.

A
Action

Authored the reference specifications — a Temporal standard and a config-driven CDK standard — then built the tooling that enforces and applies them:

  • A new-service scaffold template that generates a standard-compliant service (orchestration module, IaC, local dev stack) from day one — turning bootstrap from days into a generated starting point.
  • Internal Claude Code plugins that audit, check, and scaffold against the specs — so a standard violation is caught at review or generation time, not discovered in production.
  • Config-driven CDK adoption across services, replacing per-service infra improvisation with one referenced pattern.
R
Result

Standards moved out of docs and into the tools engineers run — enforced at PR and scaffold time rather than by memory. New services start compliant; existing ones can be audited against the spec on demand. This is the core of how I bridge the v1→v2 gap: encode quality into the agent layer instead of relying on ceremony or seniority.
